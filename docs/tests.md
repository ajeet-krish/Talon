The Python suite is the parity proof for this phase. Its test count is
unchanged at 186 and `python/tests/test_avoidance.py` is untouched, but the
module under it is now a thin re-export over `_core`, so all 20 avoidance tests
pass against the Rust geometry. The exporter is the second half of that proof:
regenerating `public/data/live/configs.json` reproduces `hover`, `waypoints`,
`obstacle_field`, and `wind` field for field, including `obstacle_field`'s
eight detoured waypoints, so the recorded obstacle-field data stays valid.

### The delegated boundary

- `bindings/src/avoidance.rs` publishes `leg_obstacle_distance`,
  `leg_intersects_obstacle`, `compute_detour_point`, `plan_avoidance_mission`,
  and `min_clearance`. Obstacles and waypoints cross as duck-typed attributes,
  so `talon.types` stays the owner of the Python dataclasses.
- One new PyO3 unit test asserts the negative-margin message the Python tests
  match on (`margin_error` is a pure function, because formatting a `PyErr`
  needs an initialized interpreter and the marshalling crate has none).
- The negative-margin contract is now enforced by every entry point that takes
  a margin, where the retired pure-Python module only raised once a leg and an
  obstacle reached the geometry. Documented in the module docstring.

### The shipped demo config

The exporter gains `avoidance`: the same circuit and the same three keep-out
spheres as `obstacle_field`, with the plain legs and the law switched on, and
the margin (2.0 m) written into the config rather than inherited from a default
that happens to match.

- The headless smoke run of that config reports 3 activations (one per
  threatened leg) and 1.68 m of minimum truth clearance against the 2 m margin,
  judged the way the recorded obstacle-field run is judged (margin less the
  1.0 m tracking tolerance that scenario allows). The deterministic native test
  for the same geometry holds 3.24 m, so the live gap is the estimator error the
  law has to steer through, which is the honest number to report.
- `src/live/view.test.ts` gains a drift guard on the shipped file: exactly one
  config enables the law, it carries zones and a positive margin, it shares the
  planned scenario's zone list, and its waypoint count is below the planned
  detour's. Dropping the block from the exporter would otherwise quietly turn
  the browser demonstration back into a pre-planned detour.

### What was not re-run or regenerated

- The frozen recordings, the validation report, and the videos are untouched.
  `fixtures/live_fixtures.json` regenerated byte-identical.
- The wasm bundle was rebuilt in 9a and is unchanged again here: this phase
  changed no Rust.
- `npm run smoke:wasm` covers the wasm engine headlessly; the R3F scene itself
  still has no automated coverage, so the new scenario's on-screen deviation is
  a human check.

### New tests

Nine of the new tests are added to `src/live/view.test.ts`:

- `altitudeLadder` (6). A 10 m mission gets 2 m rungs, 2 through 10, with 10
  flagged as the flight level. A waypoint altitude is flagged too
  (`takeoff 10, waypoint 6`). An off-grid ceiling is appended rather than lost
  (`takeoff 7` gives rungs 2, 4, 6, then the ceiling at 7). An off-grid
  waypoint altitude is flagged over the grid rung below it (`takeoff 9,
  waypoint 6` gives 2, 4, 6, 8, 9 with 6 and 9 flagged). A large mission stays
  bounded (100 m gives at most seven rungs, the highest exactly 100). A mission
  that never leaves the ground gets no ladder and no altitudes.
- `niceStep` (2). The interval snaps down to something an operator would print
  (16.67 to 10, 2.4 to 2, 0.6 to 0.5) and falls back to the finest interval
  when the value is below all of them.
- Shipped configs (1). Every scenario in the committed
  `public/data/live/configs.json` produces a non-empty ladder whose highest
  rung is its highest flown altitude and is flagged. This is the drift check
  that ties the ruler to the scenarios the app actually loads.

### The parity proof

The 186 pytest tests were written against the C++ kernel and were not touched
while the kernel moved to Rust. They now run against `talon._core`, the PyO3
extension over `talon-core`, and pass unchanged. That is the evidence that let
the C++ stack go, rather than a separate golden-vector harness.

Two call sites changed on the Python side, neither altering numerics:

- `mavlink_sil._update_derived` and `mavlink_sil._record_history` read the
  position variance through the new `Ekf.position_covariance_trace()` and
  `Ekf.position_variance()`, which sum the same three diagonal entries in the
  same order. The 200 Hz convergence check no longer converts a 15x15 nested
  list every step.
- `inject_ekf_divergence` uses `nominal()` plus `set_nominal()` instead of the
  `mutable_nominal()` aliasing hook, which PyO3 cannot express safely.

### New binding tests

- `bindings/src/convert.rs` (2): the 3-vector round trip preserves index order,
  and the 3x3 round trip is row major. These run without a GIL, so
  `cargo test -p talon-py` needs no interpreter.

`guidance`, 13 `mission`, 15 `motors`, 13 `sensors` and 21 `state_machine`

### New frontend tests (Phase 6)

- `src/live/stream.test.ts` (18): the codec closes the stride with the last
  field and reads every named offset back; a delta is appended and truncated at
  capacity; `indexAt` floors to the newest sample at or before the requested time
  and clamps at both ends (`0.016` resolves to the sample at `0.01`, not the one
  at `0.02`, because a live display may not read ahead); `poseAt` interpolates
  position, velocity, and estimate between bracketing samples, holds at the
  newest sample rather than extrapolating, takes the shortest attitude path
  across a quaternion sign flip, and refuses the empty buffer; each sample is
  tagged with the phase in effect when it was recorded, including as the core's
  timeline grows in later frames; the derived series are one per documented name
  and carry the right values from a written block.
- `src/live/pacing.test.ts` (13): nothing advances before start; 1x is one
  second of sim per second of wall time; the rate scales the target (1, 4, 16);
  `Infinity` targets the end with no wall time; pause holds and resume continues;
  a rate change re-bases on the current sim time so the vehicle never snaps; the
  run never passes the end; a 30 s tab-switch delta is clamped to `MAX_FRAME_MS`
  instead of teleporting; a negative or zero delta is ignored; reset returns to
  zero stopped; a run can start from a non-zero sim time; the rate labels are
  `1x`, `16x`, `MAX`.
- `src/live/view.test.ts` (10): the mission frame includes the takeoff column,
  contains every waypoint and the far edge of each keep-out shell, and falls back
  to a readable volume for a degenerate config; `rollPitchYaw` reads level flight
  as zero, nose-up pitch as positive, a right roll as positive, a right turn as
  positive heading, and normalizes a non-unit quaternion; the scene-from-NED
  quaternion is the documented quarter turn.
- `src/live/sim.test.ts` (8 added): the streaming passthroughs. `sampleCount`,
  `drain` (with the from-index forwarded to the session), `phases` (including a
  malformed timeline degrading to an empty list), `gpsCounts`, and `ekfFlags`.
- `src/utils/interpolation.test.ts` (2 replaced by 3): `nedToScene` puts altitude
  on the up axis, keeps a level vehicle on the ground plane, and maps the NED
  basis onto the scene basis (north to +x, east to +z, down to -y), which is the
  assertion the old test was missing.

### Live wasm smoke test (`npm run smoke:wasm`)

Flown through the built `public/wasm-rust/` module the way the page drives it,
one frame of steps at a time, draining each delta:

| Config | Samples | Last time | Last altitude | Phases | Outcome |
|--------|---------|-----------|---------------|--------|---------|
| hover | 6000 | 59.99 s | 9.99 m | 4 | holds altitude |
| waypoints | 12000 | 119.99 s | 0.00 m | 8 | 5 of 5 waypoints, landed |

Every config: the streamed stride is 36 doubles and matches the page's decoder,
one sample is recorded per control step, draining returns exactly the recorded

short of the requested duration. A paced run of the hover config at 1x over
60 Hz frames reaches the end in 3600 frames (60.00 s of wall time for 60.00 s of
sim) and never lags the wall clock by more than a frame, which is the check that
the per-frame step rounding does not drift.

| Input theta | Python `wrap_angle` (pinned by test) | Rust `wrap_to_pi` (probe) | Verdict |
|-------------|--------------------------------------|---------------------------|---------|
| `pi + 0.1` = 3.241592653589793 | -3.041592653589793 (= -pi + 0.1) | -3.04159265358979347 | MATCH |
| `-pi - 0.1` = -3.241592653589793 | +3.041592653589793 (= pi - 0.1) | -3.24159265358979320 | FAIL: equals the input, outside [-pi, pi) |
| `0.3` | 0.29999999999999982 | 0.29999999999999982 | MATCH |
| `-2*pi + 0.3` = -5.983185307179586 | 0.29999999999999982 (= 0.3) | -5.98318530717958641 | FAIL: outside [-pi, pi) |
| `-4.0` (review example) | 2.28318530717958623 | -4.00000000000000000 | FAIL: returns the input unchanged |

Confirmed: 2 of the 4 Python-pinned cases fail through the Rust formula, and
the review's `-4.0` case fails as reported. Root cause is exactly as
reported: `fmod(theta + PI, TAU) - PI` (`math.rs:48-50`) inherits libm
`fmod`'s numerator sign, so any `theta < -pi` produces a remainder in
`(-2pi, 0)` and the result stays at or below `-pi`. The Python
`(theta + pi) % (2pi) - pi` always lands in `[-pi, pi)` because Python's
modulo takes the divisor's sign. `core/src/math.rs` has zero tests (no
`#[test]`, no `#[cfg(test)]` module; 7 public functions), which is why the
defect survives both suites: the Python tests only pin the Python helper,
the Rust side pins nothing, and no Rust test asserts a `chi_d` range.
Consumer reachability re-verified: the only call site is
`core/src/guidance.rs:209`, `chi_d = wrap(chi_q + nu)` with
`chi_q in [-pi, pi]` and `nu in [-pi/2, pi/2]`, so `chi_q + nu` can reach
`-3pi/2`; `chi_d` is consumed only through `sin`/`cos` (guidance.rs:215-216,
controller.rs:167), so flown trajectories are unaffected today while the
diagnostics value can fall outside the documented range and the doc comment's
"matches the Python helper one-to-one" claim is false.

### Test quality assessment

- Assertions vs smoke: predominantly behavior assertions with quantitative
  thresholds, not smoke. Examples: EKF RMSE bounds in test_integration.py,
  clearance vs margin in the sim closed-loop tests, motor lag equality against
  the exponential closed form, wind variance against sigma, `poseAt`
  interpolation exactness, pacing lag under one frame. The smoke-flavored
  minority is `test_monte_carlo.py` (2, mostly isinstance checks),
  `test_animation.py` (2, artifact existence), and `test_plotting.py` (4).
- Determinism: no unseeded randomness anywhere. Python uses
  `np.random.default_rng(fixed)` (2026, 11, 23), Rust uses a fixed default
  seed (`sim.rs:114`, `20_261_012`), and same-seed reproducibility is itself
  asserted (`the_same_seed_reproduces_the_same_flight`,
  `test_deterministic_same_seed`). Statistical assertions are therefore
  deterministic run to run.
- Time dependence and sleeps: only `python/tests/test_mavlink_sil.py` runs
  against wall clock (three `time.sleep` calls at 5 ms and 50 ms, receiver
  timeouts of 0.5 s, thread joins up to 15 s) and binds fixed loopback UDP
  ports (15550/15551, 15570/15571), which collides if two checkouts run in
  parallel (reviews Low). Rust and vitest suites contain zero sleeps, zero
  `Instant`/`Date.now`, and zero timers. The smoke paced loop is virtual-time
  and finishes in under a second by construction.
- Network: loopback UDP only, inside test_mavlink_sil.py. vitest stubs
  `fetch` with `vi.stubGlobal`; no real network in any suite.
- Shared mutable state and order dependencies: none found. Rust tests are
  stateless per test (no `#[ignore]`, no `unsafe`, no shared fixtures),
  pytest uses function-scoped `tmp_path` and fixtures, vitest isolates per
  file. No test consumes another test's output. The one suite-level piece of
  shared state is `conftest.py`'s module-level import check: without
  `TALON_REQUIRE_CORE=1` a missing `_core` skips all 186 tests and still
  exits green. CI sets the variable; local runs must remember it (I ran with
  it set).
- Golden and recorded artifacts: `public/data/live/configs.json` is consumed
  by the app, by the smoke script (5 configs), and by two vitest drift guards
  in `src/live/view.test.ts`. By contrast `fixtures/live_fixtures.json` and
  `fixtures/sil_reference.json` are consumed by nothing, and the four
  recorded replay documents (`public/data/{gps_outage,wind,emergency,obstacle_field}.json`)
  plus `validation.json` are consumed only by the running app: no test loads
  or validates them (the store casts them to `FlightData` unchecked). The
  export tests round-trip through `tmp_path` rather than golden bytes, which
  is the right call for floats.
- Parity harness: none, as detailed in the parity section above. The one
  genuine cross-language numerical test is the dynamics RK4 oracle.

### Test-suite health verdict

Verdict: GREEN AND SOUND IN ITS CORE, WITH THREE MATERIAL BLIND SPOTS.

The suite is healthy where it exists: 543 deterministic unit and
integration tests plus 76 headless smoke checks all pass with zero warnings
in about 30 seconds of wall time total; assertions are quantitative rather
than smoke; randomness is seeded everywhere; there are no sleeps, timers, or
network dependencies outside one loopback UDP module; no order dependencies
or shared mutable state; and the closed-loop coverage (sim.rs 29 tests, the
avoidance on/off controls, the 5-config smoke) is better than typical for a
teaching simulator. The Python integration stack and the wasm seam are both
exercised end to end.

The blind spots are structural rather than flaky: (1) `core/src/math.rs`
has zero tests and already contains a verified cross-language defect, which
is the exact bug a parity harness exists to catch; (2) six duplicated
Python/Rust layers and a dead fixture pipeline mean no automated signal
connects the two implementations the project claims are one; (3) the two
standard Rust quality gates are red and ungated, and the input-validation
tests the security review called for do not exist, so all green CI currently
proves only that the happy paths still fly.

Top 3 next actions:

1. Wrap contract plus parity hardening: fix `wrap_to_pi`, add the
   `core/src/math.rs` test module (row 1), and stand up the Python-vs-Rust
   parity suite over the six duplicated layers with fixtures generated from
   the Rust side (rows 2 and 3). This is the single change that would have
   caught the High finding and prevents its recurrence.
2. Tooling gates green: clear the clippy deny error at
   `core/src/guidance.rs:52` and the 87 rustfmt hunks in 19 files, then gate
   `cargo fmt --check` and `cargo clippy --all-targets` in
   `.github/workflows/ci.yml` (add `permissions: contents: read` in the same
   edit, per the security review). Both commands are verified red today.
3. Finiteness validation with failing-first tests (rows 4 and 5) in
   `SimConfig::validate`, `ScenarioConfig::validate`,
   `AvoidanceConfig::validate`, and `validate_flight_json`, landed before
   Phase 8 mission authoring or any replay-import feature feeds user JSON to
   those parsers.

Notes for other agents: the recurring failure pattern in this repository is
"two implementations, two suites, no bridge". Any new cross-language pair
should ship with a parity test in the same change, fixtures must include at
least one corner case per wrap and branch (all current guidance fixtures sit
in the benign quadrant), and sign-based numeric validation (`v > 0.0`,
`v < 0.0`) should be replaced with an explicit `is_finite()` check plus the
range test, in Rust and Python alike. The dead fixture pipeline
(`fixtures/live_fixtures.json`, `fixtures/sil_reference.json`) should be
either regenerated from the Rust side and consumed by a pytest parity suite,
or deleted with the docstrings corrected.
