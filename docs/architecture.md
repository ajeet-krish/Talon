# Talon Architecture

Last updated: 2026-10-19 (Phase 8c)

## Current-state snapshot (FlightLab Phase 9b + hardening + Phase 5c + Phase 8c, complete)

Talon is a single-vehicle UAV GNC stack whose autopilot is one Rust library,
`talon-core`, plus a Python analysis harness and a TypeScript flight tool.
Phase 1 added deterministic obstacle avoidance and the schema 1.1 obstacle
contract; Phase 2 added the interactive 3D obstacle scene; Phase 3 turned the
replay app into Talon FlightLab, a single entry point carrying the replay,
telemetry, metrics, and video sections; Phase 4 added a live run that executed
the then-C++ kernel in the browser as WebAssembly, driven by a TypeScript port
of the Python glue. Phase 5 moves the whole autopilot into Rust (D22, D23) and
puts the browser run on it: the wasm-bindgen session in D24 replaces the
TypeScript loop, and the schema 1.1 document is now assembled in Rust (D25) so
the scene, charts, and metrics are unchanged.

Phase 5b finished the move. The autopilot is now one Rust library with two
thin wrappers: `wasm/` (wasm-bindgen) drives the browser run, and `bindings/`
(PyO3) publishes `talon._core` for the Python harness. The C++17 kernel, CMake,
Google Test, pybind11 and the Emscripten build are gone, and the `src/live/`
TypeScript autopilot modules went with them (D28). The Python harness keeps its
own higher-level layers (guidance, mission, motors, sensors, state machine,
battery) for the recorded runs, pinned against the Rust behaviour by the parity
suite (D36), while its plant, controller, estimator and wind come from the
Rust `_core`. The recorded telemetry, the validation report, and the five videos
remain frozen as produced by the Python stack and are not regenerated.

Phase 6 gave the live run a ground-station shell: a scene framed from the
mission, an instrument rail, strip charts, and per-phase teaching captions
(D26, D27). Phase 7 made altitude legible in that scene: the pad carries a
graduated ladder derived from the altitudes the mission flies, and the
vehicle's plumb line is drawn at a constant on-screen width (D31). Phase 9a
moved avoidance into the core: spherical keep-out zones and a reactive law
(D33) that substitutes a bypass point for the waypoint while a leg is
threatened (D34), with the clearance it achieved reported on the truth
trajectory. It is off by default, so every existing path is unchanged. Phase 9b
finished the move (D35): the Python planner delegates to the same geometry
through `_core`, and a fifth live config flies the plain circuit straight
through the zones with the law on, so the browser demonstrates the autopilot
avoiding each one itself.

A hardening pass then closed the parity story. `wrap_to_pi` was fixed for
negative angles and pinned by math tests, the workspace was cleared through
`cargo fmt` and `cargo clippy` with both turned into CI gates, the wasm BigInt
contract in `src/live` was fixed, and the PyO3 boundary grew the six remaining
harness layers (guidance, mission, motor mixing, state machine, sensors,
battery). An in-process pytest suite (`python/tests/test_parity_*`) now
compares the Python reference against `talon._core` directly (D36), and the
dead parity fixtures are gone.

Phase 5c then single-sourced the schema in TypeScript (D23, D37). The schema
and config types are generated by ts-rs (behind an optional `ts-export`
feature, pinned exactly) into one module, `src/types/generated/talon_core.ts`,
which also emits the parsed `SCENARIO_DEFAULTS` literal;
`src/types/flight.ts` and `src/live/types.ts` are facades over it that keep the
public import paths and the two shapes above the wire (`LiveConfig`, the
normalized required run contract, and `ScenarioDraft`, the sparse authored
config). The live run's headline numbers are no longer computed on the page:
the typed `RunSummary` is assembled in Rust by `export::run_summary` (RMSE,
final error, deduplicated phases, minimum clearance, avoidance activations)
and displayed as-is, and CI regenerates the mirror and fails on any diff so it
cannot drift from the Rust structs.

Phase 8c added the mission editor (D38). The draft is the generated
`ScenarioConfig` itself (`MissionConfig`, normalized in `src/utils/editor.ts`),
edited by a pure command and history model over a 2D top-down SVG chart
(`src/components/editor/`) with inspector panels, keyboard alternatives, and
value-equal commands as no-ops. The Zustand store
(`src/store/useMissionStore.ts`) persists only valid drafts to `localStorage`;
an invalid edit stays in memory with its errors. Validation runs the shared
`validateScenarioConfig` against the generated `LIMITS` and `SCENARIO_DEFAULTS`,
so the browser gate and the core gate agree, and import/export share a mission
as a JSON document under a 1 MB cap and the slug id contract (the reserved `live`
id included). Fly hands a validated clone to `useFlightStore.authoredMission`
and the Run view lists it first.

### Data flow (one 200 Hz SIL step)

    dynamics (truth, Rust RK4) -> motors -> wind -> sensors -> EKF -> state
    machine -> phase setpoints -> NLGL guidance -> cascaded PID -> motors

### Obstacle avoidance pipeline

Two layers share one geometry (`core/src/avoidance.rs`; the Python module is a
thin re-export of it through `_core`).

Mission planning, offline, when a detour can be worked out in advance:

    CIRCUIT_WAYPOINTS (5-leg rectangle)
        |
        v
    plan_avoidance_mission            (Rust; called from Python via _core)
        |  inserts one detour waypoint per threatened leg
        v
    augmented waypoint list (8 Waypoints) -> SILConfig.waypoints
        |
        v
    SILRunner closed loop -> SILResult -> export_sil_result_json (schema 1.1)
        |
        v
    src/ web app (R3F scene renders ObstacleField from the JSON)

Reactive, in the loop, when the world is not known until the run (D33):

    mission leg + position + velocity + obstacles
        |
        v
    ReactiveAvoidance::update
        |  threatened? -> latch a bypass point; else the waypoint
        |  clear of it? -> release, back onto the waypoint
        v
    guidance target this tick -> NLGL compute_leg -> cascaded PID
        |
        v
    SimResult.min_obstacle_clearance_m + avoidance_activations

The law is a substitution at the guidance target, so mission bookkeeping,
acceptance, and the phase machine see the mission they always saw. It is
disabled unless a scenario asks for it, and the zone list it reads is the same
`obstacles` array the document already carries.

### Module ownership

The Rust core (`core/src/`) is the autopilot and the single source of truth for
every law below. The Python package keeps its own implementations of the
higher-level layers for the recorded-run harness; the plant, controller,
estimator, wind and avoidance geometry in a Python SIL run now come from the
Rust `_core`.

| Layer | Rust core (`core/src/`) | Python (`python/talon/`) |
|-------|-------------------------|--------------------------|
| Dynamics / RK4 | `dynamics.rs` (`propagate`) | via `_core` (`bindings/`) |
| Wind | `wind.rs` (`DrydenWind`) | via `_core` (`bindings/`) |
| Controller | `controller.rs` (cascaded PID) | via `_core` (`bindings/`) |
| Estimator | `ekf.rs` (15-state MEKF) | via `_core` (`bindings/`) |
| Motors | `motors.rs` (lag + X mixer) | `motors.py` (parity-pinned harness) |
| Sensors | `sensors.rs` (truth-side IMU/GPS) | `sensors.py` (parity-pinned harness) |
| Guidance / mission | `guidance.rs` (NLGL), `mission.rs` | `guidance.py`, `mission.py` (parity-pinned harness) |
| Obstacle avoidance | `avoidance.rs` (reactive law + geometry) | `avoidance.py` (thin re-export via `_core`) |
| State machine / FDIR | `state_machine.rs` | `state_machine.py` (parity-pinned harness) |
| SIL loop | `sim.rs` (pure stepper, no transport) | `mavlink_sil.py` + `mavlink_codec.py` (MAVLink edge) |
| Battery | `battery.rs` | `battery.py` (parity-pinned harness) |
| Determinism | `rng.rs` (seeded splitmix64 + Box-Muller, `libm`) | `numpy` RNG (recorded runs only) |
| Plots / report / video | - | `plotting.py`, `export_json.py`, `animation.py` |

The Python column carries two kinds of module. Dynamics, wind, controller,
estimator and avoidance are pure delegations: thin re-exports of the Rust
`_core`, like `controller.py`, `ekf.py` and `avoidance.py`. The six layers
marked parity-pinned (guidance, mission, state machine, sensors, motors,
battery) keep an independent Python implementation, because the frozen
recorded artifacts were produced by that harness and it stays the oracle for
them. `python/tests/test_parity_*.py` compares each of the six against its
`_core` boundary in process, and every API-edge behaviour that genuinely
differs is named in `python/tests/parity_util.py` (`DIVERGENCES`) rather than
reconciled (D36). Sensor comparisons run at zero noise, because the two RNG
streams differ by design (D18).

### Schema 1.1 JSON contract

The exporter (`talon.export_json`) writes a versioned JSON document with
`meta.schema_version = "1.1"`. The new `obstacles` top-level key is a
list of `{id, center_ned, radius_m}` objects. Old 1.0 documents (without
the `obstacles` key) remain valid; the validator checks the block only
when present.

The TypeScript side of the contract is generated, not mirrored by hand (D23,
D37). ts-rs derives behind the optional `ts-export` feature emit one module,
`src/types/generated/talon_core.ts`, with the schema types, `ScenarioConfig`,
`AvoidanceConfig`, and the `SCENARIO_DEFAULTS` literal (the parsed Rust
defaults). `./scripts/gen_types.sh` is the only way to write that file (it runs
the ignored generator `core/tests/ts_export.rs`), and the CI gate regenerates
it and fails on a diff (`git diff --exit-code` over `src/types/generated`), so
the mirror cannot drift from the Rust structs that are the source of truth.
`src/types/flight.ts` and `src/live/types.ts` are facades over the generated
names: they keep the app's public import paths and the two shapes on top of the
wire, `LiveConfig` (the normalized required run contract) and `ScenarioDraft`
(the sparse authored `ScenarioConfig`).

### Web app rendering layers (Phase 2)

The R3F scene (`src/components/scene/FlightScene.tsx`) composes
static and per-frame layers over the loaded `FlightData`, plus a single
postprocessing pass:

| Layer | File | Driven by |
|-------|------|-----------|
| Ground grid | `GroundPlane.tsx` | static |
| Truth trail | `TrajectoryRibbon.tsx` | per-sample, phase-colored |
| Drone marker + camera | `DroneMarker.tsx` | truth position/velocity |
| EKF covariance | `CovarianceEllipsoid.tsx` | `position_var` |
| Wind field | `WindParticles.tsx` | `wind_ned` |
| Waypoints | `WaypointMarkers.tsx` | `waypoints_ned` |
| Keep-out zones | `ObstacleField.tsx` | `obstacles` + live clearance |
| Bloom | `FlightScene.tsx` | `@react-three/postprocessing` |

Clearance math lives in one pure module, `src/utils/clearance.ts`
(`surfaceClearance`, `minSurfaceClearance`, `clearanceBand`), shared by
`ObstacleField` (scene tint), the HUD (live readout), and the legend (flight
minimum). The 2.07 m flight-minimum the legend prints is the same quantity
the Python CI asserts, so the web readout and the validation report cannot
drift.

### Web app FlightLab shell (Phase 3)

The app is one entry point with four sections, switched by
`useFlightStore.activeView` and rendered by `ViewTabs` in the header:

| Section | File | Backed by |
|---------|------|-----------|
| Replay | `src/views/ReplayView.tsx` | R3F scene + HUD + legend |
| Telemetry | `src/views/TelemetryView.tsx` | `deriveTelemetry(data)` time-series |
| Metrics | `src/views/MetricsView.tsx` | `summarizeRun(data)` + `validation.json` |
| Videos | `src/views/VideosView.tsx` | `public/videos/*.mp4` (`RECORDINGS`) |
| Run | `src/views/RunView.tsx` | live GCS: native session + recorder + pacer |

The replay and telemetry sections share the playback clock, so the transport
bar and phase scrubber stay pinned to the bottom for both; metrics and videos
drop them. The left rail always carries the scenario list and adds the
scene-layer toggles only for the time-based sections.

Two data paths feed the screens, both derived rather than hand-maintained:

    recorded samples (public/data/*.json)
        -> deriveTelemetry  -> Telemetry charts (altitude, speed, EKF error,
                               wind, thrust, 3-sigma, clearance)
        -> summarizeRun     -> TelemetryRunSummary (duration, EKF RMS,
                               maxima, distance, min clearance)

    python/sims/run_all.py -> plots/json/validation.json -> Metrics gates table

Chart helpers live in one pure module, `src/utils/chart.ts` (min/max bucket
decimation, domain, scales, path builder), and the series derivation in
`src/utils/telemetry.ts`. Both are unit-tested in the node vitest
environment; no charting dependency is added.

### Recording pipeline

### Live in-browser run (Phase 5b)

The Run section executes the autopilot in the browser. The core is the Rust
library compiled to wasm32; the page only steps it:

    configs.json (Python-exported)  -> LiveSim (src/live/sim.ts)
      -> talon_core Session (public/wasm-rust/, wasm-bindgen, D24)
           sensors: truth-side IMU 200 Hz, GPS 10 Hz
           estimator: 15-state MEKF
           derived flags: convergence / divergence (mirrors mavlink_sil)
           state machine + FDIR
           guidance: NLGL + waypoint mission
           avoidance: reactive keep-out-zone law (off unless configured)
           controller: cascaded PID, 100 Hz ZOH
           motors: X mixer + first-order lag
           plant: RK4 + Dryden wind, ground clamp
           history at 100 Hz
      -> document_json  -> FlightData (schema 1.1, assembled in Rust, D25)
      -> summary_json   -> typed RunSummary (outcome, fix accounting, RMSE,
                           phases, clearance) for the run tiles

The module boundary is now the whole core: physics, estimation, guidance,
mission, FDIR, and the SIL loop itself are native, and the frame loop makes
about one call per frame instead of a scalar read per control tick (D22, D24).
`src/live/engine.ts` loads the wasm-pack web output at runtime from the Vite
base URL and declares the exported surface by hand (`CoreSession`, whose u64
getters are `bigint`), contract-tested against the generated
`public/wasm-rust/talon_core.d.ts` by `src/live/engine.contract.test.ts`, so a
signature drift fails the typecheck or the test instead of the run. `LiveSim`
is the seam: construct a session from the scenario JSON, step it, drain what it
recorded, and turn the finished session into the document the scene and charts
already consume.

The run summary is a passthrough (D37). `export::run_summary` in the core
computes the headline numbers from the unrounded histories it already holds:
the truth-versus-estimate RMSE and final error, the phase timeline with
consecutive duplicates collapsed, the minimum obstacle clearance, and the
avoidance activations. `summary_json()` returns that typed `RunSummary`
(generated into `src/types/generated/talon_core.ts`), `LiveRunSummary` is the
same type, and the Run view displays it as-is. No RMSE, clearance, or phase
math runs on the page; the only page-side summary left is the recorded
telemetry one (`TelemetryRunSummary` in `src/utils/telemetry.ts`), which is
computed from the rounded document the Metrics view draws.

The session streams its recorded history as flat `f64` blocks, one per
control-rate sample (`SAMPLE_STRIDE` doubles). `src/live/stream.ts` decodes them
into a recorder (`LiveBuffer`) that keeps the scene-space trail, six derived
scalar series, and the phase in effect per sample, so a frame reads what it needs
instead of recomputing anything. The decoder mirrors the Rust field offsets by
hand, and the run view asserts `sample_stride()` from the loaded build against
the local layout, so a stale wasm build fails with a message instead of showing
mislabelled numbers.

Live config flow, generated by
`python/sims/export_live_configs.py` from the Python scenario definitions:

    scenario definitions (waypoints + obstacles + detour planner)
      -> public/data/live/configs.json    (hover, waypoints, obstacle_field,
                                           avoidance, wind)

The five configs are the complete output of the exporter. Parity is not carried
by generated files (D36); the generated TypeScript mirror carries type
declarations, not fixtures.

The live run emits the same `FlightData` document a recorded scenario does,
so the scene, chart, and metrics layers are unchanged and a completed run
becomes a rail entry ("LIVE RUN") alongside the recorded scenarios. The
store keys it under the string `live` (`ScenarioKey`), which is never
fetched.

Deliberate scope limits: the core's own noise generator replaces numpy's, so a
live run is statistically equivalent to, not bit-identical with, the recorder
(D18, and the recorded files stay frozen). Fault injection (GPS
outage, emergency, low battery) is still recorded-only (D20). When the WASM
module is unavailable, Run
disables itself with a visible message and every other section still works
(D19).

### Live ground station and pacing (Phase 6)

The live run is revealed at a pace you can watch, and the Run section is laid
out as a ground station: a scene with the planned mission and the flight as it
happens, next to an instrument rail (D26).

    RunView (src/views/RunView.tsx)
      frame loop  -> Pacer.tick(dtMs)  -> target sim time (1x / 4x / 16x / MAX)
                  -> session.advance(round((target - time) / DT))
                  -> session.samples_from(cursor)  -> LiveBuffer.append
                  -> buffer.clock = session.time
      completion  -> session.document_json + summary_json -> setLiveRun('live')

Pacing is a display concern and lives entirely in `src/live/pacing.ts`. The core
has no idea it is being paced, so a watched run and a batch run of the same
scenario are the same flight; only the reveal differs. The step count comes from
the difference between the pacer's target and the session's own clock, so
per-frame rounding never accumulates into a drift, and a hidden tab's giant frame
delta is clamped rather than teleported.

Layers, all reading the same recorder:

| Layer | File | Driven by |
|-------|------|-----------|
| Ground grid | `components/scene/GroundPlane.tsx` | static, shared with the replay |
| Planned route | `components/live/LiveField.tsx` | `config.waypoints` |
| Waypoints | `components/live/LiveField.tsx` | `config.waypoints` |
| Keep-out zones | `components/live/LiveField.tsx` | `config.obstacles` + live clearance |
| Trail | `components/live/LiveTrail.tsx` | recorded samples, phase-colored |
| Vehicle | `components/live/LiveAirframe.tsx` | recorded attitude, body axes |
| Altitude ladder | `components/live/LiveAltitude.tsx` | `config.takeoff_altitude` + waypoint altitudes, static |
| Plumb line and shadow | `components/live/LiveAirframe.tsx` | the vehicle's own pose, per frame |
| Bloom | `components/live/LiveScene.tsx` | `@react-three/postprocessing` |
| Numbers, health, captions | `components/live/TelemetryRail.tsx` | `readReadout` at ~10 Hz |
| Strip charts | `components/live/LiveSpark.tsx` | recorded series |

The scene animates from the recorder's `clock` field, which the frame loop
writes, so a frame that only advances the clock costs no React work. The rail
re-renders at about 10 Hz: text has no need to keep up with 100 Hz, and the
render budget stays with the scene. `src/components/live/captions.ts` supplies
per-phase teaching text, and it names the technique rather than describing the
motion.

Two facts about presentation worth recording. The camera is framed from the
mission (start, waypoints, keep-out zones, takeoff column), not from the
trajectory, because a live trajectory is a single point on the first frame and
would drag the camera out to the launch pad. And the vehicle is drawn in body
axes with the truth attitude applied, so the nose visibly drops in cruise and
leans in a gust, with the roll and pitch in the rail agreeing with the picture.
The third fact is altitude. A shadow and a plumb line can both answer "how
high", but only a number answers "ten metres", and a number needs something
that stands still to be measured against. So the pad carries a graduated
ladder, derived from the altitudes the mission actually flies, and the vehicle
carries a plumb line drawn at a constant on-screen width so the cue survives
the zoom that a fixed-radius stem does not.

`scripts/smoke_live_wasm.mjs` (`npm run smoke:wasm`) flies every live config
through the built wasm the way the page does and asserts the outcomes, since no
browser runs in CI: sample accounting, capacity headroom, schema 1.1 on a
stepped document, per-scenario acceptance (a hold keeps altitude, a mission
lands), and that a paced 1x run tracks the wall clock without drift.

CI (`.github/workflows/ci.yml`) now gates the Rust workspace before any test
runs: `cargo fmt --all -- --check` and
`cargo clippy --workspace --all-targets -- -D warnings`, under
`permissions: contents: read`. A third gate regenerates the TypeScript mirrors
with `./scripts/gen_types.sh` and fails on any diff (`git diff --exit-code`
over `src/types/generated`), so a hand edit or a stale mirror breaks the build
rather than shipping (D37).

Test gates at Phase 8c, all from the repository root and all green: `npm test`
357 passed (20 files), `cargo test --workspace` 294 passed,
`TALON_REQUIRE_CORE=1 uv run pytest python/tests/ -q` 399 passed,
`npm run build` clean, `npm run smoke:wasm` all live checks passed.

### Mission authoring (Phase 8c)

The editor edits the document the core runs and hands it to the one run path
(D38):

    editor command (chart drag, panel field, keyboard)
      -> useMissionStore: applyCommand -> EditorHistory (undo/redo, cap 100)
      -> validateScenarioConfig + missionWarnings  (shared with the core gate)
      -> localStorage (valid drafts only; invalid edits stay in memory)
      -> Fly: toMissionConfig clone -> useFlightStore.authoredMission
      -> RunView: withAuthoredMission (authored first, own id preserved)
      -> LiveSim.create -> talon_core Session -> the existing `live` run slot

The surface is a 2D top-down SVG chart, not the r3f scene, because authoring is
measurement: waypoint drag and reorder, zone add/move/resize, wind, faults, and
parameters in the inspector panels, with keyboard alternatives for every
gesture. Chart math is pure (`src/components/editor/chart.ts`) and tested.

One warning is pre-flight. With avoidance on, a zone standing within
`radius + margin + buffer` of a planned leg is flagged before the run: a bypass
that wide on a short leg can carry the vehicle past the waypoint the leg leads
to, and the 2 m acceptance radius is then missed. Guidance has only behind-A
recovery, so the missed waypoint is never recaptured. The warning offers the two
remedies, a larger acceptance radius or moving the zone; a core past-B recovery
is deferred because it would change the Rust/Python guidance parity (D36) and
the frozen recorded artifacts.
